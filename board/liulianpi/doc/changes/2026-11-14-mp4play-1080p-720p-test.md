# 变更记录 2026-11-14：mp4play 1080p/720p 转码与 buffer 覆盖

- 日期：2026-11-14
- 主题：原始 HEVC 1080p 视频无法播放；转 H.264 做 1080p/720p 对照，并增加 capture buffer 覆盖选项

## 背景

原始文件：

```text
/mnt/VMShare/VMShare/VID_20261102_223149.mp4
```

`ffprobe`：

```text
codec_name=hevc
profile=Main
codec_tag_string=hvc1
width=1920
height=1080
r_frame_rate=30/1
audio=AAC-LC 48000Hz stereo
duration=157.7s
size=308,524,643 B
rotation=-180
```

F1C100s 的 cedrus/VE 只支持 H.264，不支持 HEVC，所以原文件无法直接播放。
另外 `/mnt/VMShare/VMShare/...` 是主机路径，目标机必须把文件放到 SD 卡上，通过
`/mnt/sd/...` 访问。

## 转码产物

主机侧用 ffmpeg 转成 H.264 Baseline + AAC：

| 文件 | 分辨率 | Profile/Level | 大小 |
| --- | --- | --- | --- |
| `VID_20261102_223149_f1c100s.mp4` | 1024x600 | Constrained Baseline 3.1 | 33,410,577 B |
| `VID_20261102_223149_1080p.mp4` | 1920x1080 | Constrained Baseline 4.0 | 93,727,155 B |
| `VID_20261102_223149_720p.mp4` | 1280x720 | Constrained Baseline 3.1 | 46,080,934 B |

共同参数：

```text
30fps，yuv420p，无 B 帧，GOP 30，AAC-LC 48kHz stereo
```

主机侧 `vdec_selftest_host -H` 对 1080p/720p 都解析出 4732 帧，POC 显示顺序正常，
没有多 slice 警告。

## mp4play `-b` 选项

1080p tiled NV12 单个 capture buffer 约 3.0 MiB。默认自动 buffer 数通常为 6，
6 × 3.0 ≈ 18 MiB，超过当前 16 MiB CMA；可能先在 `VIDIOC_REQBUFS` 报 ENOMEM。

新增：

```text
mp4play -b <buffers> file.mp4
```

- 允许 4..9，手动覆盖 capture buffer 数
- 默认行为不变（自动计算）
- 1080p 可先用 `-b 4`（约 12 MiB）或 `-b 5`（约 15 MiB）测试

## 目标机测试

```sh
mount -t vfat /dev/mmcblk0p1 /mnt/sd

# 1) 720p 对照，默认 buffer
mp4play /mnt/sd/VID_20261102_223149_720p.mp4

# 2) 1080p，默认 buffer（可能 CMA ENOMEM）
mp4play /mnt/sd/VID_20261102_223149_1080p.mp4

# 3) 1080p，降低 capture buffer
mp4play -b 4 /mnt/sd/VID_20261102_223149_1080p.mp4
mp4play -b 5 /mnt/sd/VID_20261102_223149_1080p.mp4
```

## 实测结果（16 MiB CMA）

- `720p -b 4` / `-b 5`：正常打开、解码、显示，约 30fps；
  272/284 帧后按 Ctrl-C 中断，不是解码失败
- `1080p -b 4` / `-b 5`：仍然在第一个 `3,133,440 B` buffer 上
  `cma_alloc: alloc failed`，说明 16 MiB CMA 里没有连续的 3 MiB 块
- `1080p` 默认 7 buffers：需要约 20.9 MiB，16 MiB CMA 必然失败
- `1024x600`：7 buffers 约 6.6 MiB，正常播放

结论：1080p 目前先卡在 **CMA 容量/碎片**，还没有走到 VE 分辨率判断。
720p 已经证明解码/显示链路可以跑到 30fps。

## CMA 调整

把：

```text
CONFIG_CMA_SIZE_MBYTES=16
```

改成：

```text
CONFIG_CMA_SIZE_MBYTES=32
```

32 MiB CMA 可以容纳：

- 1080p 7 buffers ≈ 20.9 MiB
- framebuffer ≈ 2.4 MiB
- 余量约 8 MiB

代价是普通内存从约 36 MiB 降到约 20 MiB。如果播放器/OOM 有问题，
可以退回 28 MiB 再试。

## 结果判断

| 现象 | 含义 |
| --- | --- |
| `vdec_open` / `VIDIOC_REQBUFS` / `ENOMEM` | CMA 不足，优先试 `-b 4/5` 或增大 CMA |
| `no free slot` | CMA 已够，DPB 需要更多 buffer；试 `-b 5/6/7` 或 `-refs 1` 重转 |
| `VIDIOC_S_FMT` / `EINVAL` | VE/驱动不支持该分辨率 |
| 能打开但 `decode failed` / 花屏 | VE 实际解码能力不足 |
| 能解码但显示异常 | frontend/DEBE 缩放或带宽限制 |
| 720p 正常 | F1C100s 实际可用上限约 720p |

## 已知限制

- 1080p 即使能解码，也要经过 frontend 缩放到 1024x600；384MHz mod clock 可能仍然紧张。
- `-b 4` 对 baseline DPB 可行，但 display 侧还押两帧，某些 GOP 可能报 `no free slot`。
- 1080p 不是当前产品的目标分辨率；这项测试只用于确认硬件上限。
